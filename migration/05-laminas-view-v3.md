# Migration: laminas-view v3 compatibility

## Scope & baseline

- `composer.json` currently pins `laminas/laminas-view: ^2.27` and `mezzio/mezzio-laminasviewrenderer: ^2.19`. The v2 bridge (`Mezzio\LaminasView\LaminasViewRendererFactory`) hard-constructs/mutates a v2 `PhpRenderer` (`new PhpRenderer()`, `setResolver()`, `setHelperPluginManager()`) and requires `laminas-view ^2.27.0` in its own `composer.json` — it cannot be installed alongside laminas-view v3.
- `mezzio/mezzio-laminasviewrenderer` **3.0.0** (published 2025-12-02) is the v3-compatible bridge. Its `composer.json` requires `laminas/laminas-servicemanager: ^4.4.0`, `laminas/laminas-view: ^3.0.1`, `mezzio/mezzio-template: ^3.0`. So a laminas-view v3 upgrade is inseparable from a **servicemanager v4** and **mezzio-template v3** upgrade — this is a coordinated ecosystem major-version bump, not an isolated change.
- 48 `use Laminas\View\...` imports across 27 files in `src/` reference APIs that changed or were removed in v3 (verified against `laminas/laminas-view` `3.0.x` branch source and its `docs/book/v3/migration/v2-to-v3.md`).
- laminas-view v3 breaking changes that hit this package directly:
  - `Laminas\View\Model\ViewModel` is now `final` and no longer has `setOption/getOption/setOptions/getOptions/clearOptions`. `ModelInterface`/`ClearableModelInterface` lost the same methods.
  - `Laminas\View\Renderer\PhpRenderer` is `final`; constructor now requires `HelperPluginManagerInterface` + `ResolverInterface` (`strictVariables` optional, defaults `true`). Removed: `init`, `setHelperPluginManager`/`getHelperPluginManager`, `setResolver`/`resolver`, `setCanRenderTrees`/`canRenderTrees`, all `Variables`-related accessors (`setVars`, `vars`, `get`, `__get`, `__isset`, `__set`, `__unset`), `plugin`/`__call`, `addTemplate`. Only `render()` and the new `setFilter(callable $filter): self` remain (single filter slot, not a chain). `render(ModelInterface $model)` still fetches the `Laminas\View\Helper\ViewModel` helper from the plugin manager and calls `->setCurrent($model)` before rendering — this is the only way left to read "the model currently being rendered".
  - `Laminas\View\Helper\AbstractHelper` and `AbstractHtmlElement` are removed entirely (no replacement base class). `Laminas\View\Helper\HelperInterface` is now an empty marker interface (no `getView`/`setView`). `HelperPluginManager::validate()` accepts `HelperInterface` or plain `callable`.
  - `Laminas\View\Variables` is removed.
  - `Laminas\View\Resolver\ResolverInterface::resolve()` signature changed to `resolve(string $name): string|false` (no renderer arg); `AggregateResolver`/`TemplatePathStack` lost several methods/constants but remain usable as before for the common case.
  - Head helpers (`HeadScript`, `HeadLink`, `HeadMeta`, `HeadTitle`, `InlineScript`, `HeadStyle`) no longer extend a shared base, are `final`, lost most of their `Placeholder`-inherited surface (`append`, `prepend`, `set`, `offsetSet*`, `getView`/`setView`, `Countable`/`ArrayAccess`/`IteratorAggregate`), and are simplified. The `HelperPluginManager` now resets all `StatefulHelperInterface` instances between render cycles automatically (`resetState()`), which is the state-buildup problem this package's proxy layer was worked around for.
- Registered laminas-view usage inventory (grep-verified):
  - `getOption`/`setOption`/`getOptions`/`setOptions`: `Generator/BlocksGenerator.php`, `Middleware/PrepareMainContentMiddleware.php`, `Layout/Layout.php`, `Toolbar/ToolbarData.php`, `Block/Container.php`, `Block/BlockPool.php`, `Block/Factory/BlockFactory.php`, `Filter/ContainerFilter.php`, `Filter/DebugFilter.php` — 39 call sites total.
  - `PhpRenderer::getFilterChain()`: `View/PhpRendererDelegatorFactory.php`.
  - `PhpRenderer::setResolver()`: `Middleware/LayoutMiddlewareFactory.php` (+ test setup in `LayoutMiddlewareTest`, `ToolbarMiddlewareTest`, `ContainerFilterTest`).
  - `PhpRenderer::vars()`/`viewModel()`: `Filter/ContainerFilter.php`, `Filter/DebugFilter.php`.
  - `extends AbstractHelper`: `View/Helper/Block.php`, `View/Helper/Layout.php`, `View/Helper/BodyClass.php`, `View/Helper/Proxy/AbstractViewHelperProxy.php`.
  - `extends AbstractHtmlElement`: `View/Helper/Wrapper.php`.
  - `extends ViewModel`: `Block/AbstractBlock.php` (and transitively `Block/Container.php`, and any consumer block).
  - `Laminas\View\Variables` type import: `Filter/DebugFilter.php`.
- Test-suite impact (grep-verified): `test/ConfigProviderTest.php` (`getFilterChain()->getFilters()`), `test/Middleware/LayoutMiddlewareTest.php` + `test/Toolbar/ToolbarMiddlewareTest.php` + `test/Filter/ContainerFilterTest.php` (`setResolver`), `test/View/Helper/BlockFactoryTest.php` + `test/View/Helper/Proxy/ViewHelperProxyAbstractFactoryTest.php` + `test/View/Helper/Proxy/AbstractProxyTest.php` (`AbstractHelper`), and option-based assertions in `test/Toolbar/ToolbarDataTest.php`, `test/Generator/BlocksGeneratorTest.php`, `test/Layout/LayoutTest.php`, `test/Block/BlockPoolTest.php`, `test/Block/ContainerTest.php`, `test/Filter/ContainerFilterTest.php`, `test/Filter/DebugFilterTest.php`, `test/Block/Factory/BlockFactoryTest.php`, `test/Middleware/PrepareMainContentMiddlewareTest.php`. `test/Bootstrap.php` builds a plain ServiceManager merging `ConLayout\ConfigProvider` + `Mezzio\LaminasView\ConfigProvider` and must track the v3 bridge's config shape.

## Decisions

1. **v3-only, no dual support.** Target `laminas-view ^3.0.1`, `mezzio-laminasviewrenderer ^3.0`, `laminas-servicemanager ^4.4`, `mezzio-template ^3`. Dual-supporting `^2.27 || ^3` was evaluated and rejected: `ViewModel` options and the `PhpRenderer` API diverge too fundamentally (filter chain vs. single filter, constructor-injected resolver vs. mutable resolver, options vs. no options) to branch at runtime without duplicating most of the package. This is a new major version of conlayout.
2. **Block metadata moves from `ViewModel` options to a single reserved variable, raw access (no accessor class).** All layout-XML `options` (`block_id`, `parent`, `order`, `before`, `after`, `container`, `wrapper`, `has_parent`, `parent_block`, `tag`, `html_*`, ...) are stored as one `stdClass` under the reserved variable key `ConLayout\Block\AbstractBlock::METADATA_KEY = '__conlayout'`, read/written directly via `getVariable('__conlayout')`/`setVariable('__conlayout', $meta)` at each call site — no `BlockMetadata`/accessor helper class. `stdClass` is chosen over a plain array because the array slot holds an object handle: fetch-once-and-mutate-by-reference avoids a get/modify/set round trip on every write (`$meta = $block->getVariable('__conlayout') ?? new stdClass(); $meta->order = 10;` needs no `setVariable` call after the first initialization). This works uniformly for conlayout blocks *and* plain `Laminas\View\Model\ViewModel` instances handed in from controllers (e.g. `ViewModelResponse`), which is the case `PrepareMainContentMiddleware::process()` needs (`setOption('has_parent', null)` on a controller-supplied model).
3. **`AbstractBlock` composes an internal `ViewModel` instead of extending it.** `Laminas\View\Model\ViewModel` is `final` in v3, so `class AbstractBlock extends ViewModel` no longer compiles. `AbstractBlock` instead `implements ModelInterface` (already required transitively via `BlockInterface extends ModelInterface, HelperInterface`) and holds a private `ViewModel $model` that every `ModelInterface` method delegates to (`getTemplate`, `setTemplate`, `getVariable`, `setVariable`, `setVariables`, `getVariables`, `clearVariables`, `addChild`, `getChildren`, `hasChildren`, `clearChildren`, `getChildrenByCaptureTo`, `setCaptureTo`, `captureTo`, `setTerminal`, `terminate`, `setAppend`, `isAppend`, `count`, `getIterator`). Composition over reimplementation: behaviour stays byte-for-byte identical to stock `ViewModel` for free, and the delegation is mechanical/one-line-per-method. `AbstractBlock` keeps its own `$view`/`setView`/`getView` (from `BlockInterface`, unrelated to the removed `ViewModel`-adjacent accessors). `Container extends AbstractBlock` is unaffected by this change (still a subclass of a non-final class).
4. **Filters read the "current model" from the injected `ViewModel` helper, not from `PhpRenderer`.** `PhpRenderer::render(ModelInterface $model)` calls `$this->pluginManager->get(ViewModelHelper::class)->setCurrent($model)` before rendering, so `ContainerFilter`/`DebugFilter` are constructed with a `Laminas\View\Helper\ViewModel $viewModelHelper` (injected from the `HelperPluginManager`, not `PhpRenderer`) and call `$viewModelHelper->getCurrent()` to get the model that was just rendered.
5. **Filter re-entrancy guard: metadata presence instead of `vars()->count()`.** v2's guard (`$vars->count()` — a nested/plain template render always has explicit vars, a model render has none) has no v3 equivalent (`vars()` is gone). Replacement: `ContainerFilter`/`DebugFilter` only act when the current model exposes `getVariable('__conlayout')` (i.e. it is a conlayout block, not a plain nested-template `ViewModel`). `ContainerFilter::filter()` additionally unsets `__conlayout` from the variables array it builds for the nested `$this->phpRenderer->render($template, $values)` call, so the inner render's "current model" (a plain `ViewModel` built internally by `PhpRenderer::render()`) carries no metadata and the filter naturally skips reprocessing it — this doubles as the re-entrancy guard, replacing the old `$this->currentViewModel === $viewModel` check.
6. **Single composed filter callable, not a chain.** `PhpRenderer::setFilter()` only accepts one callable (v2's `FilterChain` is gone). `PhpRendererDelegatorFactory` builds one closure: always wraps with `ContainerFilter`; wraps that again with `DebugFilter` when `ModuleOptions::isDebug()` is true. Order matches v2's chain priorities (`ContainerFilter` at 20 runs before `DebugFilter` at 10 in a v2 `FilterChain`, i.e. debug markers wrap the already-container-wrapped output) — composed as `$debug ? fn($v) => $debugFilter->filter($containerFilter->filter($v)) : fn($v) => $containerFilter->filter($v)`.
7. **conlayout stops constructing/mutating `PhpRenderer` and consumes the one built by laminas-view's own `ConfigProvider` + the v3 bridge's `ConfigProvider`.** In v3, `Laminas\View\ConfigProvider` registers `Renderer\PhpRenderer::class => Renderer\PhpRendererFactory::class` (constructor-injecting `HelperPluginManagerInterface` + `ResolverInterface`) and aliases `RendererInterface::class` to it. `Mezzio\LaminasView\ConfigProvider` (v3) registers its own `Resolver\AggregateResolver::class => TemplateResolverFactory::class` (built from merged `templates.map`/`templates.paths` config, including a `NamespacedPathStackResolver`) which — because it is merged after laminas-view's own config in a typical Mezzio app — is what `ResolverInterface`/`PhpRenderer` actually receive. Since conlayout already contributes `templates.paths`/`templates.map` (`con-layout::*` entries) via its own `ConfigProvider::getTemplates()`, the shared resolver already resolves conlayout templates with no extra wiring. Consequence: `Middleware/LayoutMiddlewareFactory`'s custom `createResolver()` + `$phpRenderer->setResolver(...)` call, and `config/service.config.php`'s standalone `PhpRenderer::class => PhpRenderer::class` invokable + delegator registration, are both removed; conlayout depends on `Laminas\View\Renderer\PhpRenderer::class` from the container instead of registering its own.
8. **View helpers drop their now-removed base classes; no replacement base class is introduced.** `Block`, `Layout`, `BodyClass`, `AbstractViewHelperProxy` become plain classes with `__invoke` (satisfies `HelperPluginManager::validate()` via the `callable` branch — implementing the now-empty `HelperInterface` is optional and adds no behaviour, so it is skipped). `Wrapper` and `Block/Container` (which used `AbstractHtmlElement::htmlAttribs()` and `$this->getView()->escapeHtmlAttr()` respectively — both broken, since `PhpRenderer` no longer proxies helpers via `__call`/`plugin()`) get the `Laminas\View\Helper\HtmlAttributes` helper injected through the constructor instead; `Wrapper` changes from an `invokables` entry to a factory-built helper (`WrapperFactory`).
9. **Head-helper proxies (`AbstractViewHelperProxy` + `HeadLinkProxy`/`HeadMetaProxy`/`HeadScriptProxy`/`HeadTitleProxy`/`InlineScriptProxy` + `ViewHelperProxyAbstractFactory`) are removed, and `LayoutMiddleware` calls `HelperPluginManager::resetState()` once per request instead.** The proxies exist to redeclare per-request-fresh head-helper instances (working around v2 stateful-helper buildup across requests in a long-running Mezzio process). **Source check resolved (see §Source verification):** `Mezzio\LaminasView\LaminasViewRenderer::render()` (v3) does call `$this->helpers->resetState()` at the end of every render, BUT conlayout renders blocks by calling `PhpRenderer::render()` *directly* from `LayoutMiddleware`/`ToolbarMiddleware`, bypassing `LaminasViewRenderer`, and `PhpRenderer::render()` does **not** reset state. So on conlayout's own render path the framework-level auto-reset does not fire. Therefore the proxies are removed and, to preserve fresh-per-request head-helper state under long-running runtimes (Swoole/RoadRunner/FrankenPHP), `LayoutMiddleware::process()` explicitly calls `$this->helperPluginManager->resetState()` at its very top (before `$handler->handle($request)`, so the current request's contributions are not wiped). `config/viewhelper.config.php`'s `abstract_factories` entry and `ModuleOptions::getViewHelpers()`'s `proxy` config concept are removed together with the classes. If a project needs proxied head-helper access it now uses the plain v3 helpers directly (their API shrank anyway — see baseline).

## Source verification (v3 checks)

Performed against `laminas/laminas-view` `3.0.x` and `mezzio/mezzio-laminasviewrenderer` `3.0.0` source. Resolves the three open points the prior draft flagged.

1. **`HelperPluginManager::resetState()` on conlayout's render path — NOT auto-triggered.** `Mezzio\LaminasView\LaminasViewRenderer::render()` ends with `$this->helpers->resetState();`, but conlayout's `LayoutMiddleware`/`ToolbarMiddleware` call `Laminas\View\Renderer\PhpRenderer::render()` directly (confirmed `PhpRenderer::render()` has no `resetState()` call). Outcome: decision 9 finalized — remove proxies **and** add an explicit `resetState()` call in `LayoutMiddleware` (wiring below).
2. **`Laminas\View\Helper\HtmlAttributes` — `final readonly`, constructor `__construct(EscaperInterface $escaper)`, `__invoke(iterable $attributes = []): HtmlAttributesSet`.** `HtmlAttributesSet implements Stringable`; its `__toString()` returns `''` when empty and otherwise `' ' . implode(' ', $attributes)` — i.e. a **leading space** followed by escaped, space-separated attributes, byte-compatible with the removed `AbstractHtmlElement::htmlAttribs()` for `sprintf('<%s%s>', $tag, $attrs)`. Escaping is done internally via the injected `EscaperInterface` (`escapeHtml` for names, `escapeHtmlAttr` for values). Two behaviour deltas vs. the old manual code: attribute **names are lowercased** (`array_change_key_case(..., CASE_LOWER)`) and **sorted** (`ksort()`); `class`/`rel`/`accept`/`srcset`/etc. array values are joined with a per-attribute separator. Acceptable (more correct); noted in Risks. The helper is obtained from `HelperPluginManager::get(HtmlAttributes::class)` (registered via `EscapeHelperFactory`, which supplies the configured `EscaperInterface`).
3. **`Laminas\View\Helper\BasePath` — constructor unchanged, still callable.** v3 signature is `final class BasePath implements StatefulHelperInterface` with `__construct(?string $basePath = null)` and `__invoke(?string $file = null): string`. So `BasePathFilterFactory`'s existing `new BasePathHelper($basePath)` and `BasePathFilter`'s `call_user_func($this->basePathHelper, $value)` both keep working with **no change**. One nuance: if `base_path` config is unset the factory passes `''` (not `null`), so `__invoke()` does not throw its "No base path provided" `RuntimeException`. Outcome: `BasePathFilter`/`BasePathFilterFactory` drop off the change list (verify-only, confirmed compatible).

## Implementation

### `composer.json`

- Bump `laminas/laminas-view` to `^3.0.1`.
- Bump `mezzio/mezzio-laminasviewrenderer` to `^3.0`.
- Add/bump `laminas/laminas-servicemanager` to `^4.4` (currently unpinned direct dep — pulled in transitively; pin explicitly since factories are a public contract).
- Verify `laminas/laminas-filter` (`^2.42`), `laminas/laminas-i18n` (dev, `^2.30`), `laminas/laminas-config` (`^3.10`), `laminas/laminas-eventmanager` (`^3.14`), `mezzio/mezzio` (`^3.28`) all permit servicemanager v4; bump whichever don't (`composer why-not laminas/laminas-servicemanager 4.4` after the above bumps, before touching code).
- `require-dev` `rector/rector` stays; no rule changes needed for this migration (orthogonal to `02-strict-types.md`).

### `src/Block/AbstractBlock.php`

- Change `abstract class AbstractBlock extends ViewModel implements BlockInterface` to `abstract class AbstractBlock implements BlockInterface` (drop the `use Laminas\View\Model\ViewModel;` extends-import, keep a `use` for the type of the internal instance).
- Add `private ViewModel $model;` initialized in a constructor (`public function __construct() { $this->model = new ViewModel(); }`) or inline property default — check subclasses for existing constructors first (`Container` currently has none, so a base constructor is safe; if a subclass defines its own constructor without calling `parent::__construct()`, add the call).
- Delegate every `ModelInterface` method to `$this->model`: `getTemplate(): string`, `setTemplate(string $template): static` (return `$this`, not the inner model, to preserve fluent identity), `getVariable(string $name, mixed $default = null): mixed`, `setVariable(string $name, mixed $value): static` (return `$this`), `setVariables(iterable $variables, bool $overwrite = false): static`, `getVariables(): array`, `clearVariables(): static`, `addChild(ModelInterface $child, ?string $captureTo = null, ?bool $append = null): static`, `getChildren(): array`, `hasChildren(): bool`, `clearChildren(): static`, `getChildrenByCaptureTo(string $capture, bool $recursive = true): array`, `setCaptureTo(string $capture): static`, `captureTo(): string`, `setTerminal(bool $terminate): static`, `terminate(): bool`, `setAppend(bool $append): static`, `isAppend(): bool`, `count(): int`, `getIterator(): Traversable`.
- Add `public const METADATA_KEY = '__conlayout';` here (single source of truth for the reserved variable name; `BlockPool`, `BlockFactory`, `Layout`, `BlocksGenerator`, `ToolbarData`, `Container`, `PrepareMainContentMiddleware` reference `AbstractBlock::METADATA_KEY` rather than a literal string).
- Keep `protected ?RendererInterface $view = null;` / `setView()`/`getView()` as-is (untouched by this change; `BlockInterface` still declares them).

### `src/Block/Container.php`

- No `extends`/`implements` change needed (still `extends AbstractBlock`).
- `getTag()`: replace `$this->getOption('tag', 'div')` with reading the metadata bag: `$meta = $this->getVariable(AbstractBlock::METADATA_KEY); return $meta->tag ?? 'div';`.
- `htmlAttributes()`: replace `$this->getView()->escapeHtmlAttr($value)` (broken — `RendererInterface`/`PhpRenderer` no longer proxy helpers) with the injected `Laminas\View\Helper\HtmlAttributes` helper (confirmed API in §Source verification #2). Build a plain array from the `html_*` metadata keys (strip the `html_` prefix as today) and return `(string) ($this->htmlAttributes)($attrs)` — `HtmlAttributesSet::__toString()` supplies the leading space and per-value `escapeHtmlAttr` escaping, so `openTag()`'s `'<' . $this->getTag() . $this->htmlAttributes() . '>'` stays byte-compatible. Source: `$attrs = []; foreach ((array) ($this->getVariable(AbstractBlock::METADATA_KEY) ?? new stdClass()) as $name => $value) { if (str_starts_with($name, 'html_')) { $attrs[substr($name, 5)] = $value; } } return $attrs === [] ? '' : (string) ($this->htmlAttributes)($attrs);`. Note the behaviour delta: `HtmlAttributesSet` lowercases and sorts attribute names (see Risks). Add a constructor `public function __construct(HtmlAttributes $htmlAttributes) { parent::__construct(); $this->htmlAttributes = $htmlAttributes; }` and a `ContainerFactory` (new file, `new Container($container->get(HelperPluginManager::class)->get(HtmlAttributes::class))`) since `Container` moves from `invokables` to `factories` in `ConfigProvider::getBlockConfig()` (and `'shared' => ['container' => false]` stays).

### Block metadata call-site migration (raw `getVariable`/`setVariable`, no accessor)

Pattern for every site below: replace `$model->setOption($key, $value)` with
```php
$meta = $model->getVariable(AbstractBlock::METADATA_KEY) ?? new stdClass();
$meta->{$key} = $value;
$model->setVariable(AbstractBlock::METADATA_KEY, $meta);
```
and `$model->getOption($key, $default)` with `($model->getVariable(AbstractBlock::METADATA_KEY)?->{$key}) ?? $default`. `getOptions()` (whole-bag reads) becomes `(array) ($model->getVariable(AbstractBlock::METADATA_KEY) ?? new stdClass())`.

- `src/Block/BlockPool.php`: `setOption('block_id', $blockId)` (line 46, 121), `getOption('before'/'after'/'order', ...)` (lines 88-103), `getOption('block_id')` (line 114) — all on arbitrary `ModelInterface` instances (not necessarily `AbstractBlock` subclasses, since blocks can be plain `ViewModel` per `BlockFactory`'s default `'class' => ViewModel::class`), confirming the metadata-as-variable approach (works on any `ModelInterface`, unlike an `AbstractBlock`-only accessor would).
- `src/Block/Factory/BlockFactory.php`: `$block->setOption('block_id', $blockId)` (line 75) and the `'options' => []` spec loop (lines 100-102, `foreach ($this->getOption('options', $specs) as $name => $option) { $block->setOption($name, $option); }`) — becomes building one `stdClass` from the spec's `options` array and a single `setVariable(METADATA_KEY, $meta)` call, merging in `block_id` first. Note: `$this->getOption($name, $specs)` (the factory's *own* private option-defaults helper, lines 148-153, resolving `class`/`capture_to`/`append`/`variables`/`template`/`actions` from the layout-XML spec array) is unrelated to `ModelInterface` options and is **not** touched — only the `ModelInterface::setOption`/`getOption` calls change.
- `src/Layout/Layout.php`: `$block->setOption('parent_block', $parentBlock)` (line 138), `$block->getOption('parent')` (line 192).
- `src/Generator/BlocksGenerator.php`: `$block->setOption('has_parent', true)` / `getOption('parent')` / `setOption('parent', $parentId)` (lines 61-63).
- `src/Toolbar/ToolbarData.php`: `getOption('block_id')` (lines 172, 185), the private `getOption(ModelInterface $model, string $name)` wrapper (lines 195-200, 207-210) — rename this private helper (it shadows the removed `ModelInterface::getOption` name, which is confusing now that the semantics changed) to `readMetadata(ModelInterface $model, string $name): mixed` and implement it via `$model->getVariable(AbstractBlock::METADATA_KEY)?->{$name} ?? null`.
- `src/Middleware/PrepareMainContentMiddleware.php`: `$viewModel->setOption('has_parent', null)` (line 34) on a plain controller-supplied `ViewModel` (from `ViewModelResponse`) — this is the case that specifically requires the variable-based approach to work on non-`AbstractBlock` models; becomes `$meta = $viewModel->getVariable(AbstractBlock::METADATA_KEY) ?? new stdClass(); $meta->has_parent = null; $viewModel->setVariable(AbstractBlock::METADATA_KEY, $meta);`.

### `src/View/PhpRendererDelegatorFactory.php`

- Replace `getFilterChain()->attach(...)` with `setFilter(...)`. New body:
  ```php
  $viewModelHelper = $container->get(HelperPluginManager::class)->get(ViewModelHelper::class);
  $containerFilter = new ContainerFilter($renderer, $viewModelHelper);
  $moduleOptions = $container->get(ModuleOptions::class);
  $renderer->setFilter(
      $moduleOptions->isDebug()
          ? fn (string $value): string => (new DebugFilter($renderer, $viewModelHelper))->filter($containerFilter->filter($value))
          : fn (string $value): string => $containerFilter->filter($value),
  );
  ```
  (Constructing `DebugFilter` once outside the closure is equally valid — either is fine as long as the composition order — `ContainerFilter` first, `DebugFilter` wrapping — matches decision 6.)
- Since `PhpRenderer` is no longer an invokable conlayout registers itself (decision 7), this class stays a `DelegatorFactoryInterface` on `Laminas\View\Renderer\PhpRenderer::class`, but now delegates the instance built by laminas-view's own `PhpRendererFactory` rather than conlayout's.

### `src/Filter/ContainerFilter.php`

- Constructor becomes `__construct(PhpRenderer $phpRenderer, ViewModelHelper $viewModelHelper)`.
- `filter($value)`: `$viewModel = $this->viewModelHelper->getCurrent();` (was `$this->phpRenderer->viewModel()->getCurrent()`). Guard becomes `if (!$viewModel instanceof ModelInterface) return $value;` then `$meta = $viewModel->getVariable(AbstractBlock::METADATA_KEY); if ($meta === null || $viewModel === $this->currentViewModel) return $value;` (drops the `$vars->count()` check entirely per decision 5).
- `$container = trim((string) ($meta->container ?? ''));`.
- The nested-render branch (`$values = (array) $viewModel->getVariables(); ... $value = $this->phpRenderer->render(trim($template), $values);`) must `unset($values[AbstractBlock::METADATA_KEY]);` before the loop so the nested render's model (built internally by `PhpRenderer::render(string, array)`) carries no metadata — this is what makes the inner render's filter invocation a no-op (decision 5).

### `src/Filter/DebugFilter.php`

- Drop `use Laminas\View\Variables;` (class removed) and `use Laminas\View\Helper\ViewModel;` import ambiguity — rename the local import alias if needed since both `ConLayout\Block\AbstractBlock` and `Laminas\View\Helper\ViewModel` are referenced.
- Constructor becomes `__construct(PhpRenderer $phpRenderer, ViewModelHelper $viewModelHelper)`.
- `filter($value)`: `$viewModel = $this->viewModelHelper->getCurrent();`, then `$meta = $viewModel?->getVariable(AbstractBlock::METADATA_KEY); if ($meta === null) return $value; $blockId = $meta->block_id ?? null;` — drop the `$vars->count()` check (same rationale as `ContainerFilter`).

### `src/Filter/DebugFilterFactory.php`

### `src/Middleware/LayoutMiddlewareFactory.php`

- Delete `createResolver()` and the `$phpRenderer->setResolver($this->createResolver($config['templates'] ?? []));` call (decision 7 — the container's `PhpRenderer` already has the right resolver from laminas-view's `PhpRendererFactory` + the bridge's `TemplateResolverFactory`).
- Drop the now-unused `use Laminas\View\Resolver\AggregateResolver;`, `use Laminas\View\Resolver\TemplateMapResolver;`, `use Mezzio\LaminasView\NamespacedPathStackResolver;` imports.
- Keep everything else (`$phpRenderer = $container->get(PhpRenderer::class);` stays, just without the `setResolver` mutation).
- Inject the `HelperPluginManager` into `LayoutMiddleware` (for the per-request `resetState()` call, decision 9): `$container->get(Laminas\View\HelperPluginManager::class)` as an extra constructor argument.

### `src/Middleware/LayoutMiddleware.php`

- Add a `private HelperPluginManager $helperPluginManager;` constructor dependency (see factory above).
- At the very top of `process()`, before `$response = $handler->handle($request);`, call `$this->helperPluginManager->resetState();` (decision 9 / §Source verification #1 — conlayout's direct `PhpRenderer::render()` path does not auto-reset stateful helpers, so this restores fresh-per-request head-helper state for long-running runtimes without wiping the current request's contributions).

## Risks & open points

- **`strict_variables` defaults to `true` in v3** (`Laminas\View\ConfigProvider`'s `templates.strict_variables` / `view_manager.strict_variables`). conlayout's own view scripts (`view/container.phtml`, `view/blocks/wrapper.phtml`, `view/blocks/content.phtml`, `view/toolbar.phtml`) must be audited for variable access that relied on v2's silent-null behavior; either fix the templates or explicitly set `templates.strict_variables = false` in conlayout's `ConfigProvider::getTemplates()`.
- **Transitive servicemanager v4 conflicts** are the primary feasibility gate for this whole migration — resolve before any code change (see Verification).
- **`__conlayout` leaking into `getVariables()`** — the reserved key is a real entry in the model's variable array, so anything iterating `getVariables()` for template output (the toolbar's variable dump, if any) must explicitly skip `AbstractBlock::METADATA_KEY`.
- **Decision 9 resolved (§Source verification #1):** conlayout's direct `PhpRenderer::render()` path does not auto-`resetState()`, so proxy removal is paired with an explicit `HelperPluginManager::resetState()` call in `LayoutMiddleware::process()`. No longer an open point.
- **`HtmlAttributes`/`HtmlAttributesSet` behaviour delta (§Source verification #2):** the helper lowercases and `ksort()`s attribute names and joins known list-attributes (`class`, `rel`, ...) with separators. Output for `Wrapper`/`Container` is byte-compatible for simple attributes (leading space + escaped `name="value"`) but attribute name case/order can differ from the v2 manual output; audit `view/blocks/wrapper.phtml` and any template asserting exact attribute strings.
- **`BasePath` resolved (§Source verification #3):** constructor and invoke signatures unchanged; `BasePathFilter`/`BasePathFilterFactory` need no change. No longer an open point.

## BC impact & release

- Major BC break: this is a new major version of the published `hummer2k/conlayout` package. Public-facing breaks: `AbstractBlock` no longer `extends ViewModel` (any consumer relying on `instanceof ViewModel` for a block breaks; `instanceof ModelInterface`/`BlockInterface` still holds), `ModelInterface::setOption/getOption` is gone project-wide (any consumer layout/block code calling these directly on a block breaks), the head-helper proxy classes are removed (decision 9), `Wrapper` moves from `invokables` to `factories` (transparent to consumers using the DI container, breaking only for direct `new Wrapper()` instantiation).
- Requires `laminas-view ^3.0.1`, `mezzio-laminasviewrenderer ^3.0`, `laminas-servicemanager ^4.4` at the consuming application level too (this app's `composer.json` needs the same bump, coordinated with this migration).
- Document the `__conlayout` reserved variable name and the metadata-bag pattern in `docs/layout-instructions.md` (currently documents `options` as layout-XML-facing config that becomes block options — the XML-facing `options:` key in layout updates is unchanged, only its internal storage on the model changes).
